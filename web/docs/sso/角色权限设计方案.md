# SSO 角色权限设计方案

## 文档概述

本文档定义了基于 SSO（Single Sign-On）的三级角色权限系统，用于控制用户在 CheersAI 平台中的功能访问权限和界面可见性。

**创建日期**: 2026-04-02  
**版本**: v1.0  
**状态**: 设计阶段

---

## 角色定义

### 1. 管理员（Admin）
**Casdoor 角色值**: `admin`, `owner`  
**权限级别**: 最高  
**目标用户**: 系统管理员、平台运维人员

**职责**:
- 管理整个平台的配置和用户
- 查看系统审计日志和安全信息
- 配置和管理所有 AI 功能
- 监控系统运行状态

### 2. 技术员（Technician）
**Casdoor 角色值**: `technician`, `editor`  
**权限级别**: 中等  
**目标用户**: AI 工程师、技术开发人员、配置人员

**职责**:
- 配置和管理 AI 模型
- 创建和编辑工作流
- 管理知识库和数据集
- 配置智能体和工具

### 3. 普通用户（User）
**Casdoor 角色值**: `user`, `normal`, 或空值（默认）  
**权限级别**: 基础  
**目标用户**: 最终用户、业务人员

**职责**:
- 使用已配置好的 AI 功能
- 与 Agent 对话
- 浏览和使用探索功能
- 查看个人账户信息

## 角色权限分配方案

### 方案 A：保守型（推荐）

#### 管理员（Admin）- 8 个菜单项
✅ 我的 Agent  
✅ 对话  
✅ 知识库  
✅ 智能体管理  
✅ 工作流  
✅ 应用中心  
✅ 探索  
✅ 审计日志  

**额外权限**:
- 数据脱敏配置
- Gitea 设置
- 用户管理（如果有）
- 系统设置（如果有）

#### 技术员（Technician）- 7 个菜单项
✅ 我的 Agent  
✅ 对话  
✅ 知识库  
✅ 智能体管理  
✅ 工作流  
✅ 应用中心  
✅ 探索  
❌ 审计日志（无权限）

**额外权限**:
- 可以创建和编辑 Agent
- 可以配置工作流
- 可以管理知识库
- 可以安装和配置插件

#### 普通用户（User）- 5 个菜单项
✅ 我的 Agent（仅查看和使用，不能创建/编辑）  
✅ 对话  
✅ 知识库（仅查看和搜索，不能创建/编辑）  
✅ 应用中心（仅浏览和使用，不能配置）  
✅ 探索  
❌ 智能体管理（无权限）  
❌ 工作流（无权限）  
❌ 审计日志（无权限）

**使用限制**:
- 只能使用已发布的 Agent，不能创建或编辑
- 可以与 AI 对话
- 可以查看和搜索知识库内容，但不能上传或管理文档
- 可以浏览和使用应用中心的工具，但不能安装或配置
- 可以浏览探索页面的公开内容

## 推荐方案：方案 A（平衡型）

### 理由

1. **用户友好**: 普通用户可以查看知识库和应用中心，提升使用体验
2. **清晰的职责分离**: 
   - 管理员：全局管理和监控
   - 技术员：配置和开发
   - 用户：查看和使用（只读为主）
3. **符合实际需求**: 用户需要了解可用的知识库和工具
4. **权限分层明确**: 通过功能级权限控制（只读 vs 编辑）实现安全性

## 实现建议

### 前端实现

1. **角色信息获取**
   - 从 SSO 的 `userinfo` 接口获取 `type` 字段
   - 存储在前端状态管理中（如 Context 或 Zustand）
   - 在 `currentWorkspace.role` 中映射角色

2. **角色映射规则**
   ```typescript
   // Casdoor type -> 系统角色
   admin, owner -> admin (管理员)
   technician, editor -> editor (技术员)
   user, normal, null -> normal (普通用户)
   ```

3. **权限判断逻辑**
   ```typescript
   const isAdmin = ['owner', 'admin'].includes(currentWorkspace.role)
   const isTechnician = ['owner', 'admin', 'editor'].includes(currentWorkspace.role)
   const isUser = true // 所有用户都有基础权限
   ```

4. **菜单渲染**
   - 根据角色动态生成 `navItems` 数组
   - 使用条件渲染控制菜单项可见性

5. **页面级权限控制**
   - 在页面组件中检查用户角色
   - 无权限时显示 403 页面或重定向

6. **按钮级权限控制**
   - 使用权限 Hook 或 HOC 包装按钮
   - 根据角色显示/隐藏操作按钮

### 后端实现

1. **角色信息存储**
   - 在 SSO token 交换时获取角色信息
   - 存储在用户 session 或 JWT token 中
   - 在 Account 模型中添加 `sso_role` 字段（可选）

2. **API 权限验证**
   - 在 API 端点添加角色检查装饰器
   - 验证用户角色是否有权限执行操作
   - 返回 403 错误给无权限的请求

3. **数据过滤**
   - 根据角色过滤返回的数据
   - 普通用户只能看到已发布的 Agent
   - 技术员和管理员可以看到所有数据

## 安全考虑

1. **前后端双重验证**
   - 前端隐藏 UI 元素只是用户体验优化
   - 后端必须验证每个 API 请求的权限

2. **角色信息防篡改**
   - 角色信息应存储在服务端 session 或加密的 JWT 中
   - 不应依赖前端存储的角色信息进行权限判断

3. **默认拒绝策略**
   - 未明确授权的操作应默认拒绝
   - 角色信息缺失时，应视为普通用户

4. **审计日志**
   - 记录所有权限检查失败的尝试
   - 记录角色变更操作

## 未来扩展

### 可能的新角色

1. **只读管理员（Read-only Admin）**
   - 可以查看所有内容，但不能修改
   - 适合审计人员

2. **数据管理员（Data Admin）**
   - 专注于知识库和数据管理
   - 不能配置工作流和插件

3. **应用开发者（App Developer）**

   - 不能管理知识库和插件

- 基于资源的权限（RBAC）
- 基于属性的权限（ABAC）
