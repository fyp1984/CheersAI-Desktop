# CheersAI Desktop 权限模型梳理

本文档用于统一梳理 CheersAI Desktop 当前应采用的权限逻辑，重点解决系统管理员、C_Admin 共享工作区、技术员、普通用户、个人工作区之间权限边界混乱的问题。

## 1. 核心原则

权限判断必须优先基于“当前所在工作区”和“用户在该工作区的角色”，而不是只看用户身份本身。

唯一例外是系统级内置管理员 Admin。Admin 是系统治理身份，负责统一安装和治理插件，不等同于 C_Admin 工作区管理员，也不应该自动拥有所有业务工作区的编辑权限。

可以概括为：

- Admin 管系统插件安装与系统治理。
- C_Admin 工作区管理员管公共工作区内容和成员。
- 技术员在 C_Admin 工作区负责制作智能体、工作流、应用等内容。
- 普通用户在 C_Admin 工作区只能使用公共内容，不能编辑。
- 普通用户切换到自己的个人工作区后，在自己的工作区内变成管理员/owner。

## 2. 三层权限模型

### 2.1 系统管理员 Admin

系统管理员指 `built-in/Admin` 这一类内置系统账号。

职责：

- 统一安装插件。
- 升级插件。
- 删除或治理系统级插件。
- 进入系统级后台入口，例如 `/sys-admin`。
- 做全局插件治理、系统审计、系统级运维。

不应该做的事情：

- 不应该因为是系统 Admin，就自动成为每个业务工作区的内容管理员。
- 不应该自动编辑 C_Admin 工作区或用户个人工作区里的业务内容，除非后续明确增加“系统代管”逻辑。

当前代码相关位置：

- `api/libs/desktop_auth.py`
  - `SYSTEM_ADMIN_CAPABILITIES`
  - `is_builtin_system_admin`
  - `get_system_admin_capabilities`
- `api/controllers/console/workspace/__init__.py`
  - `require_system_admin_plugin_install_capability`
- `web/app/(commonLayout)/sys-admin/layout.tsx`
  - 系统后台入口前端判断

### 2.2 C_Admin 共享工作区

C_Admin 是公共业务工作区。通过内测申请的新用户默认加入 C_Admin 工作区。

在 C_Admin 工作区中，角色和权限应按工作区成员角色生效。

C_Admin 工作区管理员：

- 可以看到完整项目。
- 可以创建、编辑、发布智能体、工作流、应用、知识库。
- 可以管理 C_Admin 工作区成员。
- 可以配置工作区级模型或资源。
- 不能安装系统插件。插件安装仍然只属于系统 Admin。

技术员：

- 可以创建、编辑、发布智能体、工作流、应用、知识库。
- 可以调试智能体和工作流。
- 可以维护公共内容。
- 不能管理成员。
- 不能安装系统插件。
- 不应拥有系统级后台权限。

普通用户：

- 可以看到 C_Admin 工作区里对所有人开放的公共智能体、工作流、应用、知识库。
- 可以运行和使用这些公共内容。
- 不能编辑、删除、发布这些公共内容。
- 不能创建或修改公共内容，除非后续产品明确允许普通用户投稿。
- 不能管理成员。
- 不能配置模型。
- 不能安装插件。

### 2.3 个人工作区

每个通过内测申请或 SSO 登录进入系统的用户，应拥有自己的个人工作区。

当用户切换到自己的个人工作区时：

- 该用户是个人工作区 owner。
- 可以创建、编辑、删除自己的智能体、工作流、应用、知识库。
- 可以管理个人工作区内的配置。
- 可以使用系统 Admin 已统一安装好的插件。
- 不能安装新的系统插件。

也就是说，同一个用户在不同工作区的权限可以不同：

- 在 C_Admin 工作区是普通用户，只能使用公共内容。
- 在自己的个人工作区是 owner，可以管理自己的内容。

当前代码中这个模型基本已经具备：

- `api/controllers/console/auth/desktop_sso.py`
  - 新用户登录时创建账号和个人工作区。
  - 根据 SSO groups 加入共享工作区。
- `api/libs/desktop_auth.py`
  - `get_account_allowed_workspace_tenant_ids` 会把 SSO group 对应工作区和个人 owner 工作区都放入可见工作区列表。

## 4. 能力点定义建议

建议把能力点分成四类：系统级、工作区管理级、内容生产级、内容使用级。

### 4.1 系统级能力

- `desktop_system_admin`
  - 系统后台入口。
  - 系统级治理。
- `desktop_plugin_install`
  - 建议新增或用 built-in Admin 判断替代。
  - 只允许系统 Admin 安装/升级/删除插件。

当前代码里没有单独的 `desktop_plugin_install`，而是通过 `desktop_sso_owner == built-in` 判断。

### 4.2 工作区管理级能力

- `desktop_team_manage`
  - 工作区设置。
- `desktop_member_manage`
  - 成员管理。
- `desktop_model_manage`
  - 模型管理。
- `desktop_model_provider_manage`
  - 模型供应商配置。
- `desktop_data_source_manage`
  - 数据源管理。
- `desktop_api_extension_manage`
  - API 扩展管理。

注意：这些是工作区级管理能力，不等于系统插件安装能力。

### 4.3 内容生产级能力

- `desktop_agent_manage`
  - 创建、编辑、调试智能体。
- `desktop_agent_test`
  - 调试智能体。
- `desktop_workflow_edit`
  - 创建、编辑工作流。
- `desktop_knowledge_edit`
  - 创建、编辑知识库。
- `desktop_app_edit`
  - 创建、编辑应用。

这些能力应给 C_Admin 管理员和技术员。

### 4.4 内容使用级能力

- `desktop_agent_use`
- `desktop_agent_view`
- `desktop_agent_run`
- `desktop_workflow_view`
- `desktop_workflow_run`
- `desktop_knowledge_view`
- `desktop_app_view`
- `desktop_app_run`
- `desktop_chat_use`
- `desktop_model_use`
- `desktop_explore_view`

这些能力应给 C_Admin 普通用户。

## 5. 当前代码中的角色能力映射

前后端都有一份角色到 capabilities 的映射：

- 后端：`api/libs/desktop_auth.py`
  - `WORKSPACE_ROLE_CAPABILITIES`
- 前端：`web/utils/workspace-capabilities.ts`
  - `WORKSPACE_ROLE_CAPABILITIES`

当前角色大致是：

- `owner`
- `admin`
- `editor`
- `normal`
- `dataset_operator`

当前 SSO 身份到工作区角色映射在：

- `api/libs/desktop_auth.py`
  - `SSO_IDENTIFIER_TO_WORKSPACE_ROLE`

例如：

- `c_admin` 映射为 `admin`
- `technician` 映射为 `editor`
- `user` / `normal` 映射为 `normal`

## 6. 当前主要混乱点

### 6.1 工作区 admin/owner 仍包含插件管理能力

当前 `owner` 和 `admin` 角色里包含：

- `desktop_plugin_manage`
- `desktop_api_extension_manage`

这会导致前端部分插件管理入口认为 C_Admin 工作区管理员可以管理插件。

但业务规则是：

- C_Admin 工作区管理员可以管理 C_Admin 工作区内容。
- 插件安装只能由系统 Admin 做。

因此需要拆清：

- 查看和使用已安装插件：普通用户也可以。
- 配置工作区内已安装插件参数：C_Admin 管理员可做。
- 安装、升级、删除系统插件：只允许系统 Admin。

### 6.2 前端按钮和后端接口判断不完全一致

后端插件安装接口已经有系统 Admin 限制：

- `require_system_admin_plugin_install_capability`

但前端部分入口还会基于 workspace capability 显示按钮或入口，容易出现：

- 前端显示可以操作。
- 点击后后端返回 403。
- 用户认为系统有 bug。

建议所有“安装插件”按钮只看系统 Admin 判断，不看工作区 admin 判断。

### 6.3 内容可见性和编辑权应分开

公共内容对所有用户可见，不代表所有用户可编辑。

当前代码中已有标签可见性基础：

- `Common`
- `通用`

相关代码：

- `api/services/tag_service.py`
  - `COMMON_VISIBILITY_TAG_NAMES`
  - `ensure_default_visibility_bindings`
  - `build_visibility_filter`

建议规则：

- C_Admin 管理员和技术员创建的应用、知识库、工作流，默认绑定 `Common/通用`。
- 普通用户可见、可运行。
- 编辑、删除、发布必须走 `*_edit` capability。

### 6.4 模型读取能力此前前后端不一致

已发现并修复一个具体问题：

- 后端允许 `desktop_model_use` 读取模型供应商。
- 前端此前只允许 `desktop_model_manage` / `desktop_model_provider_manage`。

这会导致普通用户模型列表不加载，出现模型切换 loading 或 fallback 到本地模型的问题。

已修复文件：

- `web/utils/workspace-capabilities.ts`
- `web/utils/workspace-capabilities.spec.ts`

## 7. 推荐修正方案

### 7.1 明确插件安装只属于系统 Admin

建议保留后端当前的 built-in Admin 判断，并检查所有插件安装、升级、删除接口是否都用了：

- `require_system_admin_plugin_install_capability`

前端所有安装入口统一使用：

- `hasBuiltInAdminAccess`

不要使用：

- `hasPluginManageWorkspaceCapability`

来判断安装按钮。

### 7.2 拆分插件相关能力

建议将插件能力拆成：

- 插件读取/使用：所有具备 `desktop_access` 的用户可用。
- 插件参数配置：工作区管理员可用。
- 插件安装/升级/删除：系统 Admin 可用。

如果继续复用当前能力：

- `desktop_plugin_manage` 不应再表示“安装插件”。
- 它最多表示“配置已安装插件”。

更清晰的做法是新增：

- `desktop_plugin_config`
- `desktop_plugin_install`

其中 `desktop_plugin_install` 只给 built-in Admin。

### 7.3 统一前后端角色能力表

后端和前端现在各维护一份 `WORKSPACE_ROLE_CAPABILITIES`，容易不同步。

建议：

- 短期：每次改能力表时同步改前后端，并加测试。
- 中期：让前端完全使用 `/workspaces/current` 返回的 `capabilities`，不要在前端重复推导角色能力。
- 长期：后端输出完整 capability，前端只做展示判断。

### 7.4 C_Admin 公共内容默认公开

创建公共内容时：

- 如果当前工作区是 C_Admin 或共享工作区，默认绑定 `Common/通用` 标签。
- 普通用户通过可见性过滤能看到。
- 编辑接口仍然必须要求 edit/manage capability。

这能保证：

- C_Admin 管理员和技术员制作的工作流对所有人开放。
- 普通用户不能修改公共工作流。

### 7.5 切换工作区后重新按当前工作区计算权限

用户切换工作区时，必须重新取当前工作区信息和 capabilities。

正确表现：

- 在 C_Admin 工作区，Watson1 可能是 `normal`，只能使用公共内容。
- 切到 Watson1 个人工作区，Watson1 是 `owner`，可以创建和编辑自己的内容。

如果切换后权限没有变化，说明前端缓存或后端 projection 没按 tenant 维度刷新。

相关代码：

- `web/context/app-context.tsx`
- `web/context/workspace-context.tsx`
- `web/app/components/header/account-dropdown/workplace-selector/index.tsx`
- `api/services/workspace_service.py`
- `api/libs/desktop_auth.py`

## 8. 建议最终业务口径

最终可以对外统一成下面这套说法：

1. 系统 Admin 是平台管理员，只负责插件安装、系统治理和全局运维。
2. C_Admin 是公共工作区，承载官方/团队制作的公共智能体、工作流、应用和知识库。
3. C_Admin 工作区管理员可以管理公共工作区内容和成员，但不能安装插件。
4. 技术员可以制作和维护公共内容，但不能管理成员和系统插件。
5. 普通用户在 C_Admin 工作区只能使用公共内容，不能编辑公共内容。
6. 普通用户进入自己的个人工作区后，是自己工作区的管理员，可以创建和管理自己的内容。
7. 插件采用系统统一安装，用户和工作区只能使用已安装插件，不能自行安装系统插件。

## 9. 待确认问题

下面这些需要产品或业务侧最终确认：

1. C_Admin 工作区管理员是否可以配置模型供应商 API Key？
2. 技术员是否可以调试所有公共智能体，还是只能调试自己创建的内容？
3. 普通用户是否允许在 C_Admin 工作区创建私有草稿？
4. 系统 Admin 是否需要“查看所有业务工作区内容”的审计入口？
5. 个人工作区 owner 是否允许邀请其他成员？
6. 已安装插件的参数配置权属于系统 Admin，还是属于各工作区管理员？
7. C_Admin 公共内容是否全部默认 `Common/通用`，还是允许按标签分组开放？

## 10. 推荐落地顺序

1. 先统一文档口径，也就是本文档。
2. 修正前端插件安装按钮显示逻辑，只允许 built-in Admin 看到安装入口。
3. 检查后端所有插件安装、升级、删除接口，确认都只允许 built-in Admin。
4. 调整或重命名 `desktop_plugin_manage`，避免和插件安装混用。
5. 补齐 C_Admin 普通用户、技术员、管理员三类账号的回归测试。
6. 检查工作区切换后的 capability 缓存刷新。
7. 整理 `/workspaces/current` 返回能力，尽量让前端不再重复维护角色能力表。
